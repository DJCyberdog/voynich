## VRS-105 — Jobs and Compute

- Read-only local ledger stage states, actual completed-stage denominators, checkpoint page counts when available, dependency reason, locks, generation, and last 100 redacted history events. Stage count is not a weighted completion estimate; no fabricated ETA. Detailed read validates pinned receipts/input files and page prefix. Job summary is a display snapshot, not an authorization source.
- Explicit user start of a managed detached local CPU worker using the selected compute interpreter; separate process-lifetime manager lock plus existing scheduler sweep/ownership locks. Session record contains PID and process creation time to detect stale identity; a per-session cooperative stop marker, not arbitrary PID termination. No forced kill. UI exit does not request worker stop; user may reopen UI and explicitly stop. A separate unmanaged CLI scheduler is not a managed worker; do not start competing coordinators. Interrupted/stale ledger owners require the existing explicit fenced recovery CLI.
- Actual process RSS when managed, host CPU percentage, CPU allowance, RAM and disk free using psutil and existing review-safe hardware snapshot; GPU shown NOT_MEASURED, not zero. Optional CPU thread ceiling via numerical library environment and torch thread setting; RAM/disk estimate ceilings wrap existing admission guards and pause rather than silently modify scientific settings. These are advisory per-session controls, not OS-enforced allocation limits or total workspace quotas. Zero means existing default; saved ceilings applied at managed-worker startup. No change to backend/precision/seed/recognition policy. Resource caps do not affect separately launched historical CLI workers.
- Explicit allowlisted pause/resume/cancel through original runtime CLI; control result reflects actual ledger state. Cancel requires UI confirmation. Diagnostics exposes only aggregate run counts/resource values and worker state/RSS/caps; no path, command line, PID, session ID, reviewer or private source bytes. Raw subprocess console output discarded; durable ledger event display is the available operational history. No new dependencies for ordinary monitoring beyond existing psutil.
- Automatic monitoring uses Tk background executor and quiet errors; summary sampling about every three seconds when Jobs is shown; selected detailed checkpoint verification at longer intervals to avoid constant rehashing. UI actions share one executor; no representative large-ledger responsiveness or memory benchmark established. Evidence/diagnostic views use structured local text, not final polished dashboards.

## Development entry point

From worker/ with existing Review environment (Tk, Pillow, psutil):
`python vrs_monitor.py ROOT`
ROOT must exist. Configure compatible Compute Python explicitly in Settings for authoritative registration/decision and worker controls. Start worker in Jobs; it processes explicitly registered local runs. Stop worker requests cooperative stop; check STOPPED before moving/deleting workspace. Exit desktop and stop worker are intentionally different actions. No automatic runtime install. Optional Windows tray candidate profile: requirements-tray.txt. Managed state config/vrs-operations.json and workspace/vrs101 under root; portable install/relocation/delete audit remains VRS-130.
