# VRS 0.11.0 — VRS-110–116 repository integration and private collaboration

Parent d5db38f3441f4e586933b7c0165aed10b8ab07a3. VRS-110–115 locally implemented and tested; VRS-116 BLOCKED. This is not a live production integration acceptance. Existing runtime, ledger and GUI source files remain unchanged.

## Repository transport

- Strict root-local config/repositories.json profiles: schema, repository name and numeric ID, exact visibility, base branch/commit, distinct credential environment slots, explicit publish/intake booleans and optional approved fork profile. Verify remote identity, visibility and pinned base before operations. Credentials come from environment variables, not repository config or command-line arguments; token scope enforcement is external, not independently verified here. No claim of secure persistent credential storage until VRS-131.
- Fixed HTTPS GitHub API origin, no redirects, request/response size and timeout limits. Read-only check command. Optional manual intake requires explicit profile consent and locally approved job ID, commit and exact bytes/digest; remote capability restricted to fixed local manuscript manifest reference. No automatic registration or execution, arbitrary command, URL download or remote job polling.
- Separate local publisher over existing outbox. Explicit enqueue or opt-in config/publication-routes.json routes (specific run IDs or ALL_REPORTABLE). Rebuild aggregate report from current pinned local receipts before transport, strict aggregate-only schema, UNADJUDICATED. Reports include source hashes, counts and provenance, not raw glyphs/transcriptions or reviewer IDs. Routes authorize publication, including publication of partial/failed state; owner must choose appropriate visibility. No route configured by default.
- Deterministic vrs-evidence/<report digest> branch and worker/evidence/vrs/<digest>.json. Non-forced ref update; validate exact one-file addition and complete recursive tree delta, blob bytes, base/head repository/commit and open PR identity. New PRs are draft; existing exact PR can be reconciled on retry. No write to base branch, automatic merge or generic file transport. Recheck profile consent and repo identity/base before mutations. Failure returns outbox item to PENDING; explicit generation-fenced recovery for interrupted publisher. Separate publisher lock; watch interval at least 30 seconds. Base movement or stale report requires explicit reauthorization/re-enqueue, not automatic rebasing. Branch may remain after failed or revoked publication; no automatic cleanup. External concurrent changes and consent races cannot be made globally atomic.
- Multi-repository isolation with distinct slots and nonidentical supplied tokens, explicit fork relationship/visibility/base checks. Remote GitHub REST behavior and legacy bridge parity not established natively; old bridge is unchanged and not used in the new publisher.

## Private offline collaboration

- Explicit local run and reviewer allowlist in config/collaboration.json; private_export consent. Two or more distinct configured reviewer IDs and separate HMAC key slots, cropped candidate PNG only plus inventory and randomized assignment ID. No page/locus, owner answer, model suggestion or raw context metadata in the exported assignment. Private bundle transfer must be authorized and performed by user; HMAC authenticates integrity, does not encrypt bytes. Human independence and secure key distribution remain curator-controlled.
- Immutable assignment/response files under workspace/vrs110/private; same-filesystem hard link publication with temporary file, exact retries idempotent, changed duplicate/stale queue or revision rejected. No general bidirectional sync or arbitrary data export. Offline reviewer can respond in a separate workspace. Distinguish one unique candidate from multiple review replicas. Status remains SEALED until all expected responses arrive; logical/API sealing, not encryption against filesystem owner. Curator distinct from assigned reviewers, explicit review/choice only after all responses and current revision verified. Adjudication produces local revision-bound decision draft, not final runtime submission. Existing authoritative runtime validates and accepts it only through explicit decision path. No automatic adjudication, training or scientific promotion.
